# Описание архитектурного решения

## Общая структура

Система реализована как набор независимых микросервисов, взаимодействующих между собой через HTTP API.  
Каждый сервис автономен и отвечает за свой участок бизнес-логики.

Проект разделён на несколько модулей:
- `infra` – инфраструктурные сервисы (gateway, discovery, config)
- `core` – основные бизнес-сервисы (users, events, requests)
- `stats` – сервис статистики + общий клиент и DTO


---

## Компоненты архитектуры

- **Gateway-сервер** – точка входа для всех внешних запросов. Выполняет маршрутизацию к нужным сервисам.
- **Config-сервер** – централизованное хранилище конфигураций всех микросервисов.
- **Discovery-сервер (Eureka)** – регистрация и обнаружение микросервисов внутри системы.
- **Основные микросервисы** – реализуют бизнес-логику приложения.
- **Stats-сервис** – сбор и предоставление статистики просмотров.

---

## Микросервисы

### User Service

Отвечает за:
- управление пользовательскими данными
- хранение информации о пользователях системы

Реализует:
- административное API для создания, получения и удаления пользователей
- внутреннее API для проверки существования пользователя и получения его данных другими сервисами

Расположение: `core/user-service`

---

### Event-service
Отвечает за:
- управление событиями
- категории
- комментарии
- агрегацию просмотров

Реализует:
- публичное API событий
- пользовательское API управления событиями
- административное API модерации
- 

Расположение: `core/event-service`

#### Комментарии

Функциональность работы с комментариями реализована внутри Event Service и не вынесена в отдельный микросервис.

Реализованные возможности:

- добавление комментариев к событиям

- редактирование комментариев пользователями

- удаление комментариев

- получение списка комментариев по событию

Такое решение принято из-за тесной логической связи комментариев с событиями.
При необходимости данная функциональность может быть вынесена в отдельный микросервис без изменения внешнего API.

---

### Request Service

Отвечает за:
- управление заявками на участие в событиях
- контроль статусов заявок (`PENDING`, `CONFIRMED`, `CANCELED`)
- соблюдение бизнес-правил участия в событиях (лимиты участников, необходимость модерации)

Реализует:
- пользовательское API для подачи и отмены заявок на участие
- внутреннее API для получения заявок по ID события и пользователя

Расположение: `core/request-service`

---

### Stats Service

Отвечает за:
- сбор статистики обращений к публичным эндпоинтам
- хранение информации о просмотрах событий

Реализует:
- API для записи статистических данных (hit)
- API для получения агрегированной статистики

---

## Взаимодействие сервисов

- `event-service` взаимодействует с `user-service` для получения информации о пользователях
- `event-service` взаимодействует с `request-service` для управления заявками и подсчёта подтверждённых участников
- `stats-service` используется для сбора и получения статистики просмотров
- все сервисы регистрируются в `discovery-server` и получают конфигурации из `config-server`
